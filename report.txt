Conclusion

No deterministic software fault was found in the successful SD read path that directly overlaps CS assertions or leaves active_dev set. On normal completion, SPIM configuration is restored before W5500 CS goes low, DMA buffers remain valid until EVENTS_END, and the SPI mutex covers every CS-low interval.

The strongest code-level concern is that SD cleanup can fail while FatFs still reports success. If cleanup and DMA counts are confirmed successful, SD MISO failing to tri-state remains the best match for 0xFF/garbage despite correct CS timing.

Findings

1. SD cleanup failure is discarded after successful CMD17

File/function: src/drivers/sd_spi.c:155-158, sd_end_cmd(); src/drivers/sd_spi.c:465-493, sd_read_block().

Exact path:

    spi_rx(buffer, 512);
    spi_rx(crc, 2);
    sd_end_cmd();        // return values discarded
    return SD_OK;

sd_end_cmd() calls spi_end() and spi_clock_idle(&sd_dev, 1) without checking either result. Consequently:

post-deselect clocks fail -> sd_read_block() == SD_OK -> disk_read() == RES_OK -> f_read() == FR_OK.

This directly permits the observed combination of valid file data and a damaged first W5500 access. The data and CRC transfers may have completed while the subsequent bus-release transfer failed.

Confidence: medium as root cause, high that the reporting defect exists.

Minimal diagnostic: Break on the returns from both calls in sd_end_cmd(). Record EVENTS_END, EVENTS_STOPPED, TXD.AMOUNT, and RXD.AMOUNT. Also check for SPI IDLE: TIMEOUT, although logger queue drops could hide it.

2. SPIM timeout recovery does not prove the peripheral has stopped

File/functions: src/drivers/spi.c:199-218, spi_clock_idle(); src/drivers/spi.c:379-397, spi_tx(); src/drivers/spi.c:471-489, spi_rx(); src/drivers/spi.c:573-591, spi_txrx().

Exact path:

    SPIM_TASKS_STOP_REG = 1;
    /* Wait up to 5 ms for EVENTS_STOPPED. */
    ...
    /* Clear events regardless of whether STOPPED occurred. */
    return -1;

The code does not test whether EVENTS_STOPPED was actually observed. It then allows CS deassertion, mutex release, configuration changes, new DMA pointers, and another TASKS_START.

If the post-SD idle transfer times out and STOP is incomplete, the first W5500 transfer can start while SPIM is still stopping or using old DMA descriptors. Later accesses may then return 0xFF, garbage, or stale data.

Confidence: medium. It requires an actual timeout, but finding 1 hides the idle-clock timeout from FatFs.

Minimal diagnostic: On every timeout, halt before event clearing and verify EVENTS_STOPPED == 1. At the first W5500 spi_begin(), verify SPIM is idle and no previous DMA transfer remains active.

3. W5500 callbacks suppress SPI failures and return invalid register data

File/function: src/ports/w5500_port.c:21-68; ioLibrary path third_party/Wiznet-ioLibrary/Ethernet/W5500/w5500.c:65-88.

Exact behavior:

- cs_select() logs spi_begin() failure but returns normally.
- Byte and burst writes discard spi_tx() status.
- cs_deselect() discards spi_end() status.
- Byte reads return 0xEE after a detected failure.
- Burst reads can leave stale or partially updated caller data.

The ioLibrary has no error return for these callbacks. It continues sending the header and reading data even if selection or header transmission failed. Thus the first underlying SPIM/bus error is exposed as an apparently valid getSn_SR() or getSn_MR() result.

Confidence: high as an error-masking defect, low as the initiating cause.

Minimal diagnostic: Break on every nonzero SPI return during the first post-f_read() W5500 access. Verify separately that the three-byte header spi_tx() and one-byte spi_rx() both complete with expected DMA amounts.

4. SD deselection and trailing clocks are not one atomic bus operation

File/function: src/drivers/sd_spi.c:155-158, sd_end_cmd(); src/drivers/spi.c:597-605, spi_end(); src/drivers/spi.c:98-228, spi_clock_idle().

Exact path:

1. spi_end() raises SD CS and releases the mutex.
2. spi_clock_idle() retakes the mutex and generates eight clocks.

Another task waiting on the SPI mutex can acquire the bus between these calls. Its W5500 transaction would therefore run before the SD release clocks.

The current application appears to perform both f_read() and W5500 access synchronously from net_task, with no second task currently using either SPI device. Therefore this is unlikely to explain the present reproduction, but it conflicts with the generic shared-bus transaction model.

Confidence: low for the current symptom, high that the interleaving window exists.

Minimal diagnostic: Trace task handles at every SPI mutex acquisition. Verify no transaction occurs between SD spi_end() and the following spi_clock_idle().

5. Several SD command error exits omit trailing clocks entirely

File/functions: src/drivers/sd_spi.c:33-63, sd_begin_cmd(); src/drivers/sd_spi.c:102-150, sd_exec_cmd().

Exact paths following command TX, R1 polling, or extra-response failures call only:

    spi_end();
    return error;

No post-deselect clocks are generated. A card may continue driving MISO until it receives additional clocks after CS rises.

This is not exercised by a completely successful CMD17 path. It matters if an earlier FatFs metadata read, retry, or command failed immediately before the successful operation.

Confidence: low for the stated clean read, medium if any preceding SD error occurred.

Minimal diagnostic: Trigger an R1 or command timeout and verify whether the next W5500 access occurs before any both-CS-high clocks.

6. DMA completion counts are never validated

File/functions: src/drivers/spi.c:354-400, spi_tx(); src/drivers/spi.c:448-492, spi_rx(); src/drivers/spi.c:549-594, spi_txrx().

Every transfer accepts EVENTS_END as success without checking:

- TXD.AMOUNT == TXD.MAXCNT
- RXD.AMOUNT == RXD.MAXCNT

On normal nRF52840 SPIM operation, EVENTS_END should be sufficient. However, checking amounts diagnostically would identify an aborted, short, or anomalous DMA completion at the precise SD-to-W5500 boundary.

Confidence: low as a normal-path cause.

Minimal diagnostic: Inspect amounts for:

- SD data: 512/512
- SD CRC: 2/2
- trailing clocks: 1/1
- W5500 header: 3/3
- W5500 register result: 1/1

7. W5500 burst callbacks cannot handle lengths above 512 bytes

File/function: src/ports/w5500_port.c:55-68; limit at include/drivers/spi.h:39; rejection at src/drivers/spi.c:336-343 and 422-429.

The ioLibrary passes arbitrary uint16_t burst lengths, while the SPI driver rejects anything above SPI_MAX_XFER == 512. Callback errors are then hidden.

This does not explain the one-byte getSn_SR() immediately after SD, but it can cause later networking failure during larger transfers.

Confidence: low for this failure, high as a latent incompatibility.

Minimal diagnostic: Record all W5500 burst lengths around the failure and confirm none exceeds 512.

Most Likely Non-Code Hypothesis

If all five relevant transfers complete successfully with correct DMA amounts:

1. SD 512-byte data
2. SD two-byte CRC
3. SD one-byte trailing-clock transfer
4. W5500 three-byte header
5. W5500 one-byte read

then the code contains no normal-path state transition that explains the result. At that point, SD MISO not releasing after CS rises is the leading explanation.

This is especially plausible with SD adapter modules containing active level shifters. A source holding MISO high gives 0xFF; contention between SD and W5500 can give varying garbage.

Confidence: medium-high if all SPI status/count checks pass.

Minimal diagnostic: Disconnect only SD MISO after the read, or replace the adapter with a bare socket known to tri-state DO. Also inspect MISO electrically during the both-CS-high interval and the fourth byte of the first W5500 transaction.

Verified Correct

- Both devices use SPI mode 0 and MSB-first.
- W5500 frequency is rewritten to 1 MHz before W5500 CS goes low.
- SD frequency is rewritten to 250 kHz before SD CS goes low.
- The normal CMD17 path reads all 512 bytes and both CRC bytes before deselection.
- active_dev is cleared during normal spi_end().
- Static scratch/staging buffers are protected by the bus mutex.
- Stack DMA buffers remain live until synchronous EVENTS_END.
- FatFs performs this 128-byte read by loading one 512-byte sector into FIL.buf.
- disk_read() uses independent CMD17 transactions for multiple sectors.
- No other source file directly changes either device CS during runtime transactions.
- W5500 ioLibrary keeps CS low across its header and data callback calls.
- No code was modified during the review.
